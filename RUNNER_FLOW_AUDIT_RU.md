## Что уже работает

- Host проверяет активный write-turn, его идентификатор и доступ владельца к
  Project; Project/Workspace берутся из conversation, а не из аргументов модели
  (`src/runtime.ts`, `handleDynamicTool`).
- Ручной job получает конкретный SHA, снимки конфигурации и окружения; повтор
  того же запроса использует idempotency key. Jobs одного Project сериализуются.
- Расписание хранится в SQLite, требует часовой пояс и подтверждение отдельным
  сообщением. Уникальность occurrence защищает от повторного создания обычного
  запуска, включая повтор локального времени при переходе с летнего времени.
- Service запускается из конкретного завершённого Release, хранит предыдущую
  версию для rollback и использует Docker restart policy. Ошибка обновления,
  обработанная живым процессом раннера, восстанавливает прежний контейнер.
- Агент получает live-состояние через `runner.inspect` и `service.inspect`.
  Mini App уже имеет обзор топиков и ближайших расписаний; отдельный новый
  обзорный экран для этого не требуется.

## Подтверждённые дефекты

### 1. P1 — ошибка отчёта одного проекта блокирует общий планировщик

Место: `src/runner-control.ts:1718`, `src/runner-control.ts:1852`.

`tick()` сначала ждёт `refreshExecutions()`. Исключение из доставки отчёта
выходит в общий catch, поэтому не выполняются ни отслеживание ручных jobs,
ни постановка новых запусков всех проектов. Проблемный execution остаётся
активным и повторяет эту блокировку на следующих тиках. Например, runtime
выбрасывает ошибку, если сохранённый топик доставки больше не найден; так же
может завершиться получение артефакта.

**Воспроизведение:** завершённый job с отчётом, callback доставки выбрасывает
ошибку, другое расписание уже подошло по времени. После двух тиков второй
запуск не поставлен, обработка ручных jobs не вызвана ни разу.

**Исправление:** независимо фиксировать результат выполнения и состояние
доставки; локализовать ошибки по execution/проекту. Повторять доставку через
сохранённую очередь с задержкой, не удерживая весь scheduler. Приёмочный
сценарий: недоступный адресат A не мешает запуску B и уведомлениям ручного C.

### 2. P1 — аварийное завершение deployment может оставить сервис выключенным

Место: `src/project-runner-server.ts:1832`, `src/project-runner-server.ts:458`,
`src/project-runner-server.ts:1907`.

До запуска контейнера новая версия уже записана как `activeDeploymentId`.
Затем раннер останавливает старый контейнер и создаёт новый. Если процесс
завершился между этими действиями, catch с rollback не выполняется. При старте
раннер восстанавливает состояние jobs, но не незавершённые операции services.
Старый контейнер остановлен явно, нового ещё нет; обычный `service.start`
пытается запустить отсутствующий контейнер новой версии и тоже завершается
ошибкой.

**Воспроизведение:** в фикстуре существующего service-теста восстановлено
сохранённое состояние именно этой фазы: новая версия активна, прежняя
остановлена, новая не создана. Новый экземпляр раннера показывает `failed`,
прежний контейнер не восстанавливается, `start` отклоняется. Это моделирование
состояния после аварии, а не реальное выключение Docker или сервера.

**Исправление:** журнал операций с идентификатором и фазой, отдельно текущая
работающая и кандидатная версии. При старте сверять сохранённую фазу с Docker,
детерминированно завершать операцию или восстанавливать прежний Release.
Отдельно покрыть аварии до остановки, после остановки, после создания и после
прохождения health check.

### 3. P2 — старое подтверждение отменяет свежую паузу и воскрешает удалённое расписание

Место: `src/runner-control.ts:630`, `src/runner-control.ts:662`.

План хранит полную копию расписания. При применении проверяются scope, actor,
следующий turn и срок действия токена, но не версия текущей записи. `UPSERT`
перезаписывает новые значения и может создать запись заново после удаления.

**Воспроизведение:** A планирует переименование включённого расписания; B
ставит его на паузу; A подтверждает старый план — расписание снова включено.
Другой вариант: B подтверждает удаление, затем A подтверждает ранее
подготовленное изменение — удалённое расписание появляется снова.

**Исправление:** монотонный номер версии и `expectedVersion` в плане;
применение через условное обновление в транзакции. Различать create и update,
а delete также сверять с ожидаемой версией. При конфликте показать актуальную
конфигурацию и сформировать новый план. Один timestamp недостаточен для двух
изменений в одну миллисекунду.

### 4. P2 — запуск по расписанию может бесконечно брать устаревший код

Место: `src/runner-control.ts:1755`, `src/git-inspector.ts:1180`.

Выбор default branch работает через локальные `refs/remotes/origin/*`.
Путь запуска расписания не обновляет эти refs с Git-сервера. Пока другой
действующий механизм не выполнит fetch, свежий опубликованный коммит
не попадёт в job. Комментарий об актуальной опубликованной ветке и ожидания
владельца расходятся с фактическим источником SHA.

**Воспроизведение:** временный bare-репозиторий origin содержит версию 2,
локальный `origin/master` — версию 1. Реальный `tick()` передаёт в `submit`
SHA версии 1. Внешняя сеть и публикация в настоящий origin не использовались.

**Исправление:** для режима «последняя опубликованная версия» обновлять refs
перед выбором SHA через существующий безопасный слой Git, с ограничением
времени и общей блокировкой на репозиторий. При недоступном origin явно
фиксировать сбой подготовки либо заранее согласованную политику работы со
старой версией. Отдельным режимом можно добавить закреплённый Release.

### 5. P2 — принятый раннером job теряется для scheduler при потере ответа

Место: `src/runner-control.ts:1761`, `src/runner-control.ts:1780`,
`src/runner-control.ts:1809`.

Между принятием job удалённым раннером и сохранением `jobId` есть окно.
При потере ответа submit помечает execution как `failed` без `jobId`.
После аварии процесса оставшийся `claimed` через минуту тоже переводится в
`failed`, без поиска по idempotency key. Уникальность occurrence препятствует
повторному claim, но не восстанавливает связь с уже работающей job. Финальный
результат и доставка по этому расписанию больше не отслеживаются.

**Воспроизведение:** mock submit сначала сохраняет работающий job с metadata,
затем выбрасывает ошибку потери ответа. Два тика оставляют execution в `failed`
с пустым `jobId`, хотя job существует. Отдельно проверен просроченный `claimed`:
он становится `failed` без попытки сверки с раннером.

**Исправление:** сохранять ключ, выбранный SHA и данные подготовки до submit;
неопределённый исход переводить в состояние сверки. Искать принятый job по
ключу и восстанавливать связь. Повторять создание можно только с тем же ключом
и тем же payload, когда серверная дедупликация это гарантирует; автоматически
создавать новый production job с новым ключом нельзя.

### 6. P2 — уведомления о завершении могут исчезать без повторной попытки

Место: `src/runner-control.ts:1854`, `src/runner-control.ts:1868`.

Ошибка передачи lifecycle-сообщения в outbox только логируется. Затем
execution становится terminal и исчезает из `activeExecutions()`, поэтому
повторной попытки нет. Ошибка уведомления владельцев после сохранения terminal
статуса имеет аналогичное окно; runtime также использует `Promise.allSettled`
для личных сообщений владельцам. Наличие durable outbox не спасает событие,
которое ещё не удалось в неё поставить.

**Воспроизведение:** первая попытка lifecycle-уведомления выбрасывает временную
ошибку. После второго тика число попыток остаётся равным одному, execution
уже `completed`.

**Исправление:** хранить намерение отправки и статус доставки независимо от
job/execution. Для всех событий использовать стабильный ключ и восстановление
недоставленных записей после рестарта; окончательные ошибки показывать владельцу.

### 7. P2 — изменение расписания меняет адресата уже выполняющегося запуска

Место: `src/runner-control.ts:813`, `src/runner-control.ts:1841`.

Execution не хранит снимок политики доставки. При завершении берутся
`delivery`, `deliveryCondition`, `notifications` и `updatedBy` из текущей
записи расписания. Если владелец поменял адресата для будущих запусков,
предыдущий job тоже отправит отчёт в новое место. Удаление расписания до
окончания job убирает его настройку доставки из этого пути целиком.

**Воспроизведение:** execution создан при адресате topic 10; до окончания
изменён только адресат расписания на topic 20. Callback отчёта получает
topic 20.

**Исправление:** сохранять конфигурацию, автора и версию расписания в execution.
По умолчанию изменения применяются к будущим occurrences. Перенаправление
отчёта уже запущенной job должно быть отдельным явным действием. Доставку по
сохранённому снимку всё равно проверять по актуальным правилам доступа.

### Производительность вычисления времени

`nextScheduleOccurrence` перебирает минуты до восьми суток, каждый раз создавая
новый `Intl.DateTimeFormat` (`src/runner-control.ts:307`, `:357`). Один расчёт
еженедельного расписания сразу после наступившего времени занял **327 мс**
на локальном Node 24.19.0; это единичный замер, не оценка production latency.
Всё это время занят поток JavaScript. При большом числе расписаний задержка
накапливается. Новый Mini App кеширует ближайшее время, но `runner.inspect`
по-прежнему вычисляет его для каждого запроса.

Стоит кешировать форматтеры по timezone и рассчитывать кандидаты по дням,
а не создавать форматтер на каждую минуту. Сохранить проверки пропущенного и
повторённого локального времени при DST; отдельно проверить resume и создание
расписания внутри grace-окна, чтобы не запускать прошлое occurrence неожиданно.
