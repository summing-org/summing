# 2026-08-20

## Approval bridge принимает связанные редакционные правки заказчика

- Runner фиксирует маршрут доставки из encrypted environment snapshot: точные
  `REPORT_CHAT_ID`/`REPORT_THREAD_ID` (с fallback на approval route) и до 20
  `APPROVER_USER_IDS`. Отчёт нельзя повторно связать с другим chat/topic/user
  scope; пользовательский MTProto-аккаунт в согласовании не участвует.
- `@hash0_bot` показывает кнопки **Одобрить / Нужны правки / Отклонить**.
  Комментарий принимается только от allowlisted Telegram user ID и только reply
  к конкретному report message или связанному ForceReply prompt. Durable event
  содержит `planId`, SHA-256, ID отчёта, ID комментария, автора, время и bounded
  текст, не меняя writable `approval.json` контейнера.
- `changes_requested` монтируется в следующий dry-run read-only. Project adapter
  повторно сверяет plan/digest, фиксирует правки у старого плана и передаёт их
  генератору как редакционные данные, которые не могут отменять формат,
  безопасность, источники и forbidden topics. Новый план получает новый digest.
- Conversation Understanding schema больше не отправляет неподдерживаемый
  OpenAI Structured Outputs keyword `uniqueItems`; уникальность event IDs
  по-прежнему строго проверяет локальный parser.

## Восстановлено автоматическое обновление production SUMMING

- Deployment видел актуальный `origin/master` и успешно проходил сборку и 200
  тестов, но откатывался на этапе `runner-host`: старый установленный unit с
  `ProtectHome=true` скрывал user bus, а последующий `read-only` bootstrap не
  позволял впервые создать rootless Docker socket в `/run/user/990`.
- На host сохранена резервная копия unit, применён уже находившийся в master
  `ProtectHome=read-only`, исправлен владелец только runner-каталога `.config` и
  однократно инициализирован штатный rootless Docker.
- Повторный deployment завершился на `536f360` / `9.16.4`; SUMMING, Project
  runner, rootless Docker, deploy timer и path-unit активны, application и runner
  health checks проходят без новых warning/error после запуска.

## Project approval вынесен в постоянный Telegram bot bridge

- Успешный manual dry-run может оставить bounded `approval-request.json` с
  `planId`, SHA-256, `report.html` и относительным pending state внутри project
  data. Runner проверяет regular-file/symlink/traversal границы и сохраняет
  отдельное durable approval event вне writable volume контейнера.
- SUMMING отправляет отчёт основным Bot API в исходную Project conversation,
  связывает callback с точными `chat_id`, `message_thread_id`, `message_id` и
  actor user ID, затем показывает кнопки одобрения/отклонения. Повторы одного
  решения идемпотентны, смена решения и чужой callback отклоняются.
- Callback намеренно не переводит project `approval.json` в `approved`. Следующий
  live-run получает read-only event, сверяет plan/digest и только фиксирует
  решение; публикация остаётся отдельным вторым live-run. Bot token и чтение
  Telegram history project-контейнеру для approval больше не требуются.

## Artifact download token имеет единственное каноническое представление

- Viewer отклоняет неканонические Base64URL-сегменты до AES-GCM-дешифрования.
  Изменённая строка download token больше не принимается даже тогда, когда
  permissive decoder преобразует её в те же байты из-за незначащих padding bits.
- Регрессия отдельно проверяет криптографически изменённый token и его
  byte-equivalent неканонический alias, устраняя случайное падение deployment
  test на ответе `200` вместо `401`.
