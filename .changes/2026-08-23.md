# 2026-08-23

## Separate finite Jobs from desired-state Services

- Split Project workload semantics into two host-scoped control planes. `runner` continues to own
  finite `build`/`validate`/`dry-run`/`run` jobs and schedules, while the new `service` namespace
  owns `inspect`, `deploy`, `start`, `stop`, `restart`, `rollback`, and bounded secret-redacted
  logs for long-running API, web, and worker processes. Services never consume a job slot after
  deployment and do not inherit the 12-hour live-run timeout.
- Added strict `.summing/services.json` version 1 manifests with named services, bounded optional
  commands, container ports, HTTP health paths, and startup timeouts. Deploy activates an exact
  completed non-build Release only after rechecking source/config/encrypted-environment hashes and
  immutable image ID. API/web ports are allocated from a configurable range and exposed only on
  `127.0.0.1`; public Caddy routing remains an explicit separate operation.
- Added crash-recoverable service state and rootless Docker lifecycle. Containers use the existing
  read-only/capability/resource sandbox plus `restart=unless-stopped` and service-scoped persistent
  data. Update retains current and previous deployments, restores the previous container when
  startup/health fails, and supports exact rollback; restart reuses the current Release without a
  build. Runner protocol advanced to 3 and production units define ports `20000..29999` by default.
- Project Viewer now renders Services and finite Jobs as separate diagnostic sections and exposes
  service status/logs without adding deployment buttons. Added manifest, agent-tool, Viewer API,
  durable restart, deployment, stop/start, upgrade, and rollback coverage. Version advanced to
  9.20.0.

## Lightweight runner releases and parallel projects

- Each accepted runner job now becomes a small reproducible release record: the job stores its
  `releaseId`, source archive SHA-256, exact config snapshot and SHA-256, encrypted environment
  revision, and immutable Docker image ID. Source, environment, and config payloads are retained
  for the newest 20 terminal jobs per Project; the existing 100-job metadata/log retention remains.
- Replaced the single global worker with a bounded dispatcher. Up to
  `SUMMING_RUNNER_MAX_PARALLEL_JOBS` independent Projects run concurrently (default 2), while jobs
  for one Project stay serialized because they share its writable data volume. The queue skips a
  blocked same-Project job so a later independent Project is not starved. Live-run timeout is now
  configurable through `SUMMING_RUNNER_RUN_TIMEOUT_HOURS` with a 12-hour production default.
- Runner health now reports product/protocol versions plus queued, running, and parallel-capacity
  counters. `runner.inspect` exposes node-wide capacity alongside Project-local state, and Project
  Viewer labels jobs with their short release ID and environment revision.
- Added integration coverage for release evidence, bounded retention, health metadata, and two
  concurrent Projects. No new per-action network or data policy was introduced; the pre-existing
  validation isolation remains unchanged. Version advanced to 9.19.0.
- Added explicit, idempotent `runner.replay` for a retained non-build Release. A replay keeps the
  original `releaseId` while receiving a new job ID, verifies source/config/encrypted-environment
  hashes, reuses the saved environment revision and immutable image ID, and fails closed when any
  payload expired or the image disappeared. The agent tool warns that external production side
  effects may run again and is available only for an exact inspected job ID.
- Removed the external Project name from production deployment. The repository no longer ships a
  Project-specific runner JSON/env/schedule or systemd service/timer. Viewer/runner installation is
  generic; an old timer is disabled only when its exact basename is supplied through
  `SUMMING_LEGACY_PROJECT_UNIT`. Environment cutover likewise has no guessed default Project and
  runs only with an explicit `SUMMING_ENV_MIGRATION_PROJECT`.

## SUMMING 9.18 — logical Project Portal routes and delivery control plane

- Replaced infrastructure-facing portal selection with stable business `portalKey` values such as
  `main`, `reports`, and `legal`. `project_portal_bindings` keeps transport-neutral destination
  metadata, enforces one key per Project/Workspace, and a partial unique index guarantees at most
  one default; migration turns the first existing external Telegram binding into default `main`.
  Sends and runner messages without a key resolve the default, while an explicit unknown key fails
  closed instead of guessing a Telegram topic.
- Extended generic runner `portal-messages.json` with an optional per-message `portalKey`. A batch
  can target several logical portals while preserving the existing default-route behavior and the
  same durable transport used by an interactive Project agent.
- Hardened the filesystem outbox with bounded draining, five-attempt dead-letter handling, active
  record/byte quotas, terminal notification to the originating internal Conversation, retention,
  administrator Retry/Cancel, and delivery observability in Admin Mini App. A record left in
  `sending` by a process crash now becomes `uncertain` and is never retried automatically, because
  Telegram may already have accepted it.
- Added encrypted durable inbound portal artifacts. Files are persisted only after secret scanning,
  encrypted with a node-local AES-256-GCM key, integrity-bound by SHA-256, scoped to the originating
  Project/event, and pruned with Team Space raw retention. History returns `artifactId` metadata;
  only an active authorized owner turn can materialize it under `.summing-runtime/attachments/` or
  forward it. `project_portal.send` accepts batches of up to ten workspace paths or artifact IDs.
- Expanded common Project portal history with optional route, author, time, event-range, text, and
  attachment filters while keeping every customer message untrusted evidence rather than approval,
  requirements, or execution authority.
- Admin Mini App now edits `portalKey` and default on each external binding and displays outbox
  status, attempts, errors, Retry, and Cancel. Slash binding remains a recovery path with optional
  `[portalKey] [default]` arguments.
- Node recovery now carries portal outbox and encrypted artifacts; the artifact key is included only
  with `INCLUDE SECRETS`. Added `release:version` and `release:check` so package, lockfile, runtime,
  VERSION, README, and handbook versions move together. Version advanced to 9.18.0.
