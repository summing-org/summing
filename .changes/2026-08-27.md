# 2026-08-27

## Release 9.28.0

- Advanced SUMMING from `9.27.0` to `9.28.0` for the complete native Project
  portal media contract.

## Deliver every caption-capable portal artifact through its native Telegram type

- Centralized the Project portal message kinds as `text`, `document`, `photo`,
  `audio`, `video`, `animation` and `voice`; runner capture, durable outbox
  validation and delivery now share the same exhaustive type instead of
  maintaining partial string unions.
- Runner protocol 6 accepts bounded numbered native artifacts with strict
  filename, MIME, regular-file and size validation: JPEG/PNG photos, MP3/M4A
  audio, MP4 video, GIF/MP4 animation and OGG/MP3/M4A voice.
- Telegram delivery maps each attachment to its exact multipart method and
  field (`sendDocument`, `sendPhoto`, `sendAudio`, `sendVideo`,
  `sendAnimation`, `sendVoice`) while preserving caption, topic, reply,
  checksum, idempotency and uncertain-delivery semantics.

## Release 9.27.0

- Advanced SUMMING from `9.26.0` to `9.27.0` for native video delivery from
  completed live runner jobs.

## Deliver bounded live-run videos through Project portals

- Live `run` jobs now receive the same job-scoped artifact directory and portal
  transport metadata as `dry-run`, so one run cannot overwrite or hide another
  run's report bundle. Completed live jobs capture `portal-messages.json`, expose
  their retained artifact count and participate in the same bounded retention.
- Extended runner protocol 5 with a strict `video` portal-message kind and
  `video-NN.mp4` allowlist. MP4s must be ordinary non-symlink files with exact
  `video/mp4` type and at most 20 MB; binary bytes travel over a dedicated Unix
  socket endpoint instead of lossy UTF-8 JSON conversion.
- Durable Project portal outbox records preserve whether an attachment is a
  document or video. Native videos use Telegram `sendVideo` with streaming
  enabled, while retaining the existing checksum, idempotency, retry,
  dead-letter and uncertain-delivery guarantees. Viewer downloads use the same
  binary-safe path.
- Manual and scheduled completed live jobs now route captured messages through
  the same exact portal/topic resolution used by dry-runs. Regression coverage
  spans runner capture, binary retrieval, MIME rejection, outbox persistence,
  manual live-job notification and native multipart Telegram delivery.

## Release 9.26.0

- Advanced SUMMING from `9.25.0` to `9.26.0` for result-scoped customer
  discussions without Project observer bindings.

## Separate result context from Project context

- Added Project-independent `customer_channels`, durable `result_publications`,
  reply-chain `result_discussion_messages`, and result-linked `project_feedback`.
  A channel acquires Project correlation only through one concrete publication;
  the same external topic can therefore receive unrelated projects' results
  without gaining either Project context.
- Direct replies to a report or a subsequent agent answer now run in an ephemeral
  environment with `workspaceAccess=false`. The model sees only customer-safe
  producer metadata, the delivered report, its bounded artifact, and that result's
  discussion; repository files, Git metadata, Project memory, owner conversations,
  and Team Space retrieval are excluded.
- Customer replies are persisted as untrusted feedback and notify the matching
  primary working topic. Consent-visible feedback is available through the revised
  read-only `project_context` tool and is injected into the next owner run, but it
  never becomes intent or starts work without an explicit owner instruction.
- Retired observer creation from Admin and Telegram, `/publish` fan-out, active
  observer routing, startup processors, and the `project_portal` host-tool namespace.
  Existing observer rows and legacy portal routes remain intact, migrate into the
  customer-channel catalog, and stay available only for history and compatible
  delivery of already-created records.
- Updated Admin, help, README, operator handbook, capability migration, and
  regression coverage for exact result delivery, discussion correlation, feedback,
  legacy migration, and the absence of repository access.

## Release 9.25.0

- Advanced SUMMING from `9.24.0` to `9.25.0` for exact scheduled-report
  destinations and reply-scoped read-only Project context.

## Decouple scheduled reports from observer topics

- Scheduled `dry-run` plans can now resolve a Telegram topic by its exact human
  name and persist the resulting `chat_id/topic_id` plus display label. If the
  name is unavailable or ambiguous, an owner can mention the bot in the target
  forum topic with «отчёты сюда» and reuse that short-lived exact marker while
  confirming the plan. Neither path creates a Project/observer binding.
- Completed scheduled dry-runs now hand their declared report batch to the
  durable filesystem outbox before the scheduler marks the execution complete.
  Direct-topic records retain the existing idempotency, checksum, retry,
  dead-letter and uncertain-delivery behavior. A report destination is
  independent of each generated message's legacy `portalKey`; only schedules
  migrated without an exact destination continue to use legacy routing.
- A direct reply to a delivered report is correlated through its sent outbox
  record. It receives an ephemeral read-only Project snapshot and up to 64,000
  characters of the exact report artifact for that question only, with no
  network, write tools, persistent Conversation or observer relationship.
  Ordinary messages in the same topic remain unbound.
- Project observers remain available as an optional, separate mechanism for
  continuous read-only Q&A, published updates and durable feedback. Updated the
  README, operator handbook and Admin outbox wording to make this boundary and
  the legacy-only role of `portalKey` explicit.
- Added legacy schedule migration, exact destination resolution, marker,
  direct outbox, scheduled transport and report-reply regressions. Node 24
  lint/build, release consistency, the focused 45-test suite and the complete
  247/247 suite pass.

## Rename topic bindings to Telegram

- Renamed the Admin Mini App section «Привязки топиков» to the broader and shorter «Telegram» in both the navigation tab and page heading. The specific controls remain grouped under «Маршрутизация топиков» and «Доставка заказчику».

## Add atomic generated-secret provisioning

- Added a separate manual `provision` runner action backed by a pinned
  `.summing/provisioning.json` profile. Projects declare exact generated outputs,
  target environment variables, byte limits, and optional one-shot inputs to
  consume without weakening the standard dry-run artifact allowlist.
- Provision workloads return one strict private `0600` result through an
  ephemeral bind mount. Their stdout/stderr is suppressed, the handoff is
  removed on every exit and startup recovery, and job/audit metadata records
  only profile and variable names plus environment revisions. Provision source,
  config, and encrypted input snapshots are removed immediately instead of
  consuming retained Release slots.
- Successful results are promoted directly into the AES-256-GCM project
  environment with field-level conflict detection. Provision jobs require a
  clean committed worktree and cannot be scheduled, replayed, or deployed as
  services.
- Added manifest/result validation, encrypted environment promotion, runner
  integration, legacy job-watch migration, secret-output suppression, cleanup,
  and policy regression coverage.

## Make Telegram media retries durable across TDLib restarts

- Enabled TDLib's file database and added stable `remote.id` / `unique_id`
  references to every new media job. Durable job deduplication and content
  references no longer depend solely on the process-local numeric `file.id`.
- Media retry now resolves a current numeric file ID from the stable remote
  reference, falling back to rereading the original Telegram message for
  legacy jobs. The refreshed payload is persisted before download so later
  retries remain bound to the same attachment.
- On startup, ready connectors requeue pre-v2 failed media jobs once. The
  transition atomically moves their counters from `media_failed` back to
  `media_pending`; ordinary manual requeue now balances those counters too.
- Media errors identify their actual pipeline boundary as
  `telegram-resolve`, `telegram-download`, `object-store-put`, or
  `object-store-delete`, avoiding the previous ambiguous `Access Denied`
  label in the S3 status card.
- Regression coverage verifies persistent TDLib file metadata, stable job
  payloads, legacy message rehydration, counter repair, and stage-qualified
  errors.

## Silence primary binding and background model egress

- Primary topic bind/rebind now follows the same silent group behavior as an

  confirmation surface.

- Legacy `model_egress_announced_at` and `egress-notice` intervention records stay
  readable for database and portable-bundle compatibility, but runtime no longer
  creates new ones.
- Remaining proactive group output is limited to optional orientation/proactive
  replies when their dedicated switch is enabled, plus operational runner and

  delivery remain explicit-action outputs.

## Release 9.23.0

- Advanced SUMMING from `9.22.0` to `9.23.0` for silent group enrollment,
  indefinite raw evidence retention, and removal of the participant/admin memory
  control commands.

## Keep consented group collection silent and unbounded

- Joining a Telegram group still records membership provenance and creates its
  Team Space, but no longer sends or audits a durable-observation admission
  message. The legacy `team_memory.announce_on_join` key is ignored.
- Binding or rebinding an observer topic no longer posts a project explanation
  into that topic. The existing primary-topic owner notification remains because
  it identifies the single write-authority table.
- Removed `/memory_me`, `/memory_forget_me`, `/memory_resume_me`, `/memory_pause`,
  and `/memory_resume` from dispatch, help, configuration documentation, and the
  operator handbook. `/memory` and `/memory_status` remain read-only status views.
- Removed `team_memory.raw_retention_days` and the runtime's startup/daily purge.
  Raw Team Space events, attachment metadata, and encrypted observer artifacts
  now have no age-based expiry; artifacts are created with `expiresAt = null`.
  Explicit erasure through the signed consent ledger and credential interception
  remain separate safety boundaries.

## Group-output audit

- Remaining proactive group outputs are the primary-topic owner binding notice,
  the first model-egress disclosure when background understanding is enabled,
  and optional orientation/proactive replies when their separate Admin switch is
  enabled. Operational runner notifications and terminal delivery warnings may
  also target their originating primary topic.
- Explicit user/agent actions still produce ordinary replies, streamed results,
  files, `/publish` updates to observers, targeted portal deliveries, and safety
  warnings for intercepted credentials. Deployment and knowledge-sync lifecycle
  notifications remain owner-private rather than group messages.

## Release 9.22.0

- Bumped SUMMING from `9.21.1` to `9.22.0` for signed group-wide consent,
  complete MTProto history admission, and durable recovery of previously skipped
  history.

## Use signed group consent for complete Telegram backfill

- Admin now records one source-level agreement covering `history`, `future`, and
  `model_egress` for all historical, current, and future authors. Internally the
  existing portable consent ledger uses the reserved Telegram user ID `0`, so
  Team Space export/import carries the agreement without a second consent table.
- A new MTProto source cannot start without the signed group agreement. Unknown
  authors, bot-authored records, anonymous chat senders, and senderless service
  events are admitted immediately under that agreement; the Bot API no longer
  has to observe every participant before backfill.
- Individual revocation is an explicit per-user deny that overrides the group
  agreement for ingest, model egress, attachments, erasure, and future events.
  Revoking an author who had no individual row now creates a durable override
  instead of silently leaving group access active.

## Recover old consent-skips without deleting their audit trail

- Granting consent to an already synchronized source with unresolved skips now
  requests a separate `team_sync_history_recovery` operation. Its state,
  checkpoint, recovered count, error, and timestamps survive process restart and
  do not overwrite the primary collection checkpoint.
- Recovery rereads MTProto history idempotently. Existing message revisions are
  ignored; only a newly persisted canonical event increments `accepted` and
  reduces `skipped`. If initial collection is unfinished, it completes first and
  recovery starts afterwards; pause defers both safely.
- `team_sync_unknown_authors` retains the original message count and adds an
  additive `recovered_count`. Admin status and `/sync_status` show only the
  unresolved difference while preserving the original attribution for audit and
  allowing a future revoke to create a new unresolved interval.
- Group consent is honored by attachment and document model-egress checks, while
  an exact revoked identity still denies every reference. Portable imports accept
  both legacy author rows and the new recovered counter.
- Admin wording now describes the signed whole-group contract, makes an empty
  historical boundary explicitly mean all available history, and exposes group
  consent plus recovery progress on each source card.
