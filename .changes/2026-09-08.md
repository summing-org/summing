## Версия 9.36.1: возврат из проекта в «Управление»

- В Project Viewer, открытом из карточки топика или по ссылке на его модель
  в админке, появилась компактная кнопка «← Управление». Она возвращает прямо
  во вкладку Telegram независимо от числа просмотренных вкладок проекта.
  При обычном открытии проекта из Telegram эта кнопка скрыта.
- Тот же переход подключён к штатной кнопке Telegram через
  [BackButton API](https://core.telegram.org/bots/webapps#backbutton).
  Обработчик снимается при уходе со страницы и восстанавливается на pageshow;
  в админке штатная стрелка скрывается. Кнопка внутри страницы работает
  без SDK и сохраняется на экране ошибки загрузки проекта.

  вкладок, топиков и перезагрузке Viewer. Это только признак происхождения
  перехода: серверная авторизация не меняется. Возврат всегда использует
  фиксированный локальный путь `/admin?section=bindings&restore=1`.
- Перед уходом админка сохраняет только фильтр списка и его вертикальную/
  горизонтальную прокрутку в `sessionStorage.summingAdminReturn`. При явном
  возврате эти значения проверяются и восстанавливаются после загрузки списка;
  одноразовый параметр restore удаляется из URL. Недоступный или повреждённый
  storage не блокирует навигацию. Формы и секреты в этот снимок не входят.
- Обе кнопки возврата используют существующую проверку несохранённых настроек
  модели и окружения: отмена подтверждения оставляет пользователя в проекте.
  Обычное открытие ссылки в новой вкладке сохраняет стандартное поведение браузера.
- Версия поднята до 9.36.1 штатным release-скриптом, метаданные и документация
  синхронизированы. Зависимости установлены отдельно в task worktree.

## Надёжность задач, расписаний и доставки результатов

- Исправлены пункты 1, 3, 4, 5, 6 и 7 аудита `RUNNER_FLOW_AUDIT_RU.md`:
  исключение доставки не блокирует scheduler; принятый scheduled job восстанавливается
  после потери ответа; уведомления переживают restart; старый план не отменяет
  свежую паузу/правку и не воссоздаёт удалённое расписание; запуск использует
  опубликованный commit после fetch; уже начатый execution сохраняет адресата.
- В SQLite добавлен журнал `runner_delivery_intents`. Terminal status execution и
  намерения отправки фиксируются одной транзакцией; у manual watches так же
  фиксируются started-события и передача terminal-уведомлений в журнал.
  Отчёт, lifecycle-сообщения и уведомление владельца независимы и имеют стабильные
  ключи. По 50 готовых намерений передаются в существующий Telegram outbox;
  неуспешная передача повторяется с backoff 15 секунд → 30 минут после restart.
  Отдельная delivery-drain promise не задерживает периодические scheduler ticks;
  graceful shutdown дожидается и текущего tick, и доставки.
- Личные уведомления владельцев и сообщения в исходный рабочий топик теперь тоже
  сохраняются в outbox, по отдельной записи на адресата. Ошибка одного владельца
  не теряет уведомление и не повторяет уже принятую отправку другому. Фактическая
  доставка проверяет текущих owners/binding и права автора отчёта/lifecycle.
  Передача в outbox отделена от Telegram I/O. `runner.inspect` возвращает ошибки
  передачи с числом попыток/следующей попыткой и исполнения, в том числе после
  удаления расписания.
- Перед scheduled submit сохраняются точный idempotency key, metadata, выбранный
  commit и SHA-256 архива. Неопределённый исход остаётся `reconciling`; сверка
  проверяет scope, action, occurrence, revision и доступный archive digest.
  Новый scoped GET `/jobs/lookup` ищет по job ID либо idempotency key за пределами
  recent-page из 50 jobs; он используется и для восстановления manual watches.
  Прерванные HTTP-ответы клиента отклоняют promise вместо зависания/необработанной
  ошибки. Автоматического повторного production submit нет: неопределённый job
  удерживает overlap, а если раннер не подтверждает job, нужна проверка оператором.
- Расписания получили монотонную целочисленную `version`; план хранит
  `expectedVersion`, применение проверяет её под `BEGIN IMMEDIATE`. Pause/resume
  тоже увеличивают версию, включая несколько действий в одну миллисекунду.
  Claim повторно проверяет наличие, версию и enabled-состояние расписания, чтобы
  устаревший снимок scheduler не запустил уже выключенную/удалённую запись.
- Execution хранит полный снимок настроек/автора/адресата. Cascade deletion убран:
  удаление прекращает будущие запуски, сохраняя историю и доставку текущих.
  Миграция существующих execution атомарно переносит строки и снимает конфигурацию
  на момент обновления; утраченную ранее историю восстановить нельзя. Старые планы
  без expectedVersion требуют нового подтверждения.
- Scheduled fetch проходит безопасную проверку Git config/endpoint, использует
  управляемый SSH credential и общую с Viewer блокировку по canonical Git common
  directory. Не меняет checkout/ветку; при ошибке fetch нет fallback на старый SHA.
  Кеш форматтеров IANA timezone ограничен 128 элементами и убирает создание
  `Intl.DateTimeFormat` на каждую перебираемую минуту; DST-правила сохранены.
- Проверки: полный набор **329/329** на Node 24.19.0; build, TypeScript lint,
  `release:check` (согласованная версия 9.34.1), `git diff --check`.
  Регрессии покрывают потерянный submit/HTTP response, старый claim, scoped lookup
  вне recent-page, несовпадение payload, restart до уведомления, независимые retry
  отчёта/lifecycle/владельцев, медленную доставку, смену/удаление адресата,
  конфликт plan/pause/delete, миграцию исполнения и stale/failing origin.
  Использованы локальные Git fixtures, тестовые Unix-сокеты и подставные Telegram
  transport/runner ответы; внешние jobs и production-сервисы не запускались.
- README и аудит обновлены. Восстановление незавершённого service deployment,
  расширение Mini App, preview/история пропусков и семантика create/resume внутри
  grace-окна остаются отдельными этапами. Production и origin не изменялись.

## Аудит джобов, расписаний и сервисов рабочего топика

- Добавлен `RUNNER_FLOW_AUDIT_RU.md`: проверен путь от Project/Workspace и
  активного owner-turn до ручного job, scheduled occurrence, постоянного service
  и доставки результата. Аудит актуализирован поверх Mini App «Обзор» (`4e7cdd5`).
- Подтверждены семь дефектов: исключение доставки блокирует общий scheduler;
  авария между остановкой прежнего service-контейнера и созданием нового не
  восстанавливается при старте раннера; старый schedule plan отменяет паузу или
  воссоздаёт удалённое расписание; scheduled submit использует не обновлённый
  remote-tracking SHA; потеря ответа submit оставляет принятый job без связи с
  execution; lifecycle-уведомление теряется при ошибке до приёма в outbox;
  изменение адресата расписания влияет на уже выполняющийся job.
- Зафиксированы необходимые инварианты: отдельно хранить execution и delivery,
  сверять неопределённый submit по сохранённому ключу и payload, журналировать
  фазы service deployment, проверять монотонную версию schedule plan и хранить
  снимок политики доставки в execution с актуальной проверкой доступа.
- Предложены порядок исправлений и дополнения к существующему обзору: причины
  ожидания jobs, понятный preview расписания, история пропусков, здоровье
  сервисов и рабочий топик уведомлений. Единичный локальный замер расчёта
  следующего недельного запуска составил 327 мс; описана оптимизация без
  изменения DST-инвариантов.
- Проверки: сборка на Node 24.19.0, 33 теста раннера, доступа и Mini App,
  восемь дополнительных
  контролируемых сценариев. Сервисная авария моделировалась сохранённым состоянием
  с имитацией Docker. Production-сервисы и отправка сообщений не использовались;
  прикладной код в этой итерации не менялся.

## Mini App: обзор проекта и переключение рабочих топиков

- Project Viewer по умолчанию открывает «Обзор»: активные и подготавливаемые задачи,
  количество ожидающих сообщений, последние ошибки топиков, восемь последних
  результатов и три ближайших запуска с часовым поясом и местом доставки отчёта.
  Даты расписаний вычисляются существующим планировщиком; ближайшее время
  кешируется до изменения расписания или наступления этого времени.
- Добавлен read-only `/api/viewer/overview`. Авторизация проверяется при каждом
  запросе; выборка ограничена текущими editable bindings одного Project/Workspace.
  История повторно сопоставляет неизменяемые project/workspace запуска с текущей
  привязкой conversation. После rebind чужие результаты, другие workspaces и
  observer conversations не попадают в обзор. Тексты ограничены 240 символами для
  запроса/ошибки и 600 для результата; внутренние thread IDs и пути не выдаются.
- Переключатель показывает доступные рабочие топики, основной маршрут и статусы;
  ссылки открывают соответствующий топик Telegram. Смена conversation сохраняет
  раздел и заново загружает документ: ответы прежнего контекста не могут обновить
  новый экран. Несохранённые модель/effort и переменные защищены подтверждением.
- Статусы обновляются раз в пять секунд; запросы объединяются, скрытое окно
  прекращает polling, ошибки увеличивают интервал до 30 секунд. При отсутствии
  связи остаются данные с временем последнего успешного обновления. Настройки
  автоматически не перечитываются; неизменившийся DOM результатов сохраняется,
  раскрытые результаты восстанавливаются при обновлении списка.
- Обзор не зависит от Git/runner I/O; сбой загрузки репозитория оставляет его
  доступным. Файлы загружаются при открытии вкладки. Обновление раздела раннера
  перечитывает статусы jobs/services. Новая разметка, стили и логика обзора вынесены
  в `viewer-overview-assets.ts` и адаптированы под телефон и светлую/тёмную тему.
- Исправлена потеря ввода при позднем ответе загрузки переменных: редактор и
  сохранение ждут исходную revision; повторный запрос объединяется, переход между
  вкладками сохраняет черновик, явная перезагрузка спрашивает об его отмене.
- Проверка на Node 24.19.0: все 302 теста проходят, сборка и TypeScript lint
  проходят. Браузерная проверка на тестовых данных подтвердила ширины 320/390 px,
  стартовый обзор, переключение ветки/топика, сохранность черновика при polling,
  отмену перехода, светлую тему, обзор без Git и восстановление после потери связи.
  Production не изменялся.
