# 2026-08-31

## Release 9.30.0

- Advanced SUMMING from `9.29.0` to `9.30.0` for exact, owner-scoped external
  Telegram messaging and controllable runner lifecycle notifications.

## Exact multi-group external messaging without logical keys

- Added the active `external_message` host namespace. A Project owner can list,
  bind, unbind, read history from, and send arbitrary text or up to ten safe files
  to a required exact `(chatId, topicId)` pair. There are no public `portalKey`,
  content/release entities, or user-managed idempotency keys.
- Added a many-to-many `project_topic_destinations` allowlist. One Project can use
  topics in multiple customer, test, or statistics groups, and one exact topic can
  be shared by multiple Project scopes. Every send rechecks the active owner turn,
  Project/Workspace and exact pair before entering the durable outbox.
- Preserved retry, dead-letter, uncertain-delivery and idempotency guarantees as
  internal transport behavior. A repeated host tool call deduplicates from its
  turn/call identity; a new intentional call remains a new message.
- Admin → Telegram now presents `Рабочий` and `Внешний` bindings. A topic may stay
  the single primary conversation while also carrying any number of exact external
  Project routes; no alias input is shown.

## Passive incoming history and shared encrypted attachments

- Exact external topics remain passive observation surfaces: messages are recorded
  without reply or `@mention`, never start Project Q&A/commands, and never become
  intent, approval, or instructions. Consent-visible history is filtered by the
  active Project's exact routes.
- New inbound attachments are encrypted once against their Team Source rather than
  copied per Project. Materialization and forwarding authorize the event source
  against the active Project allowlist; version-1 Project-scoped artifacts remain
  readable for compatibility.
- Existing logical portal bindings migrate into exact destination rows on startup.
  Legacy `project_portal_bindings` and manifest keys remain only for old scheduled
  report routes; the owner-facing contract uses exact IDs.

## Explicit job outcome conditions

- Manual jobs and schedules can define up to twelve exact lifecycle messages for
  `started`, `succeeded`, `failed`, and `finished`. The same primitive works for
  Build, Validate, Dry run, Live run, and Provision, validates every destination
  against the Project allowlist, and queues through the durable outbox even after
  the initiating Codex turn has ended.
- Lifecycle text supports `{{jobId}}`, `{{action}}`, `{{status}}`, `{{error}}`, and
  `{{revision}}`. Thus an exit code 1 can deliberately produce a detailed failure
  report, an always-terminal message, or no external notification at all.
- Kept bounded `portal-messages.json` artifact batches isolated to Dry run/Live run.
  Their scheduled `deliveryCondition` remains `success`, `failure`, or `always`;
  arbitrary Build/Validate/Provision artifacts are not silently granted external
  egress.
